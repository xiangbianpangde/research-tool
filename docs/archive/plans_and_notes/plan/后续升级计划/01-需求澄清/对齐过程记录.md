## 四、PM 洞察记录

### 4.1 V1.0 第 0 轮洞察

**类型**：缺口识别
**内容**：用户提"无缝接入"但没说"知识树"具体形态——默认按"知识树 = front matter tags 集合"理解，落到 F-016。
**风险**：若用户实际"知识树"是图谱结构，F-016 需重做。

### 4.2 V1.0 第 1 轮洞察

**类型**：冲突预警
**内容**：用户要求"用 deepseek-v4-flash"（硬约束 1）但 BiliNote 默认支持 OpenAI/DeepSeek/Qwen 三家。若 deepseek-v4-flash 在某场景（如超长 context）不可用，R-003 的回退路径是什么？
**解决方案**：预留 F-013 多供应商回退，但回退目标限定为 qwen-turbo（不动 deepseek 硬约束）。

### 4.3 V1.0 第 1 轮洞察（第二条）

**类型**：模式识别
**内容**：用户 5 大硬约束中有 4 个是"约束"（不是"功能"），说明用户偏好"明确边界 + 不越界"的设计哲学。
**落实**：边界章节 B-001~B-010 全部锁定，BiliNote 移植仅取 60% 核心能力，剩余 40% 不动。

### 4.4 V1.1 第 2 轮洞察

**类型**：缺口识别（**新增**）
**内容**：RA 调研发现 deepseek-v4-flash 实测支持 1M context（远超 V1.0 假设 64k 15 倍）——V1.0 中 F-005 的 60s 总结约束是**过紧的**，可以接受更大输入。
**解决方案**：F-005.AC-2 扩为 ≤ 20k input / 4k output（PM 决策选项 A：单次整合），不采纳分段 map-reduce（章节连贯性优先）。

### 4.5 V1.1 第 2 轮洞察（第二条）

**类型**：冲突预警（**新增**）
**内容**：RA 调研发现 BiliNote 默认 Whisper 是 `tiny`（性能妥协），本集成如直接沿用 V1.0 tiny 假设会牺牲质量。RA 建议改 medium，但 medium 1.5GB 可能在低 RAM 机器 OOM。
**解决方案**：F-014 增 `--transcriber-size` 参数；CLI 启动时检测 RAM < 8G 自动降档 base/small；F-004 默认 medium。

### 4.6 V1.1 第 2 轮洞察（第三条）

**类型**：收敛预判（**新增**）
**内容**：V1.1 修订采纳率 12/12 = 100%，无驳回项；D4 提升 0.15 后达到 0.90；CCI 提升至 0.960 已远超 0.90 交付线。
**结论**：V1.1 可作为终版交付 SA-001 / DD-001 / 第⑦棒 / 第⑧棒。
