## TDR-002 选定混合架构（主方案 A）

```
[决策编号] TDR-002
[决策标题] 选定混合架构（管道-过滤器 + 分层 + 横切）
[决策状态] 已接受
[决策内容] V1.1 采用混合架构：核心主链管道-过滤器 + CLI 入口分层 + 错误日志横切
[决策理由]
  1. 业务流以数据处理为主，管道-过滤器天然契合

  - 纯分层（方案 B）: DTO 维护成本高，管道语义丢失 → 拒绝
  - 微服务: V1.1 单机假设被打破，引入网络延迟 → 拒绝
  - 纯事件驱动: BP 顺序固定，事件总线反而增加复杂度 → 拒绝
[影响范围] 全部 12 模块
[相关TDR] TDR-003 / TDR-005
[来源标注] [TD:ADR-001] [TD:AC-方案对比]
```

## TDR-004 缓存采用 sqlite + WAL 模式

```
[决策编号] TDR-004
[决策标题] 缓存采用 sqlite + WAL 模式
[决策状态] 已接受
[决策内容] M-004 缓存使用 sqlite 3.x + WAL 模式，路径 ~/.cache/research-tool/cache.db
[决策理由]
  1. V1.1 单机假设下 sqlite 足够（10k 条目 / 5GB 上限）

  - LevelDB/RocksDB: 需额外依赖
[影响范围] M-004 / DP-004
[相关TDR] TDR-011 (V2.0 迁移)
[来源标注] [TD:ADR-004] [调研:S-102]

## TDR-006 并发上限 3 + URL 上限 10

```
[决策编号] TDR-006
[决策标题] 并发上限 3 + URL 上限 10
[决策状态] 已接受
[决策内容] BP-011 固定并发上限 3（asyncio.Semaphore(3)），单次入参 URL 上限 10
[决策理由]
  1. 性能约束 [PRD:F-008.AC-1] 3 个 30 分钟视频 ≤ 12 分钟
  2. URL > 10 队列上限 [PRD:F-008 边界]
  3. 3 并发 × medium = 6-12GB RAM
  4. M-012.IF-030 资源探测可自适应降到 2
[拒绝的替代方案]
  - 并发 5: 资源不足（5×medium = 10-20GB）
  - URL 上限 50: 长时间队列影响用户体验
[影响范围] M-012 / M-001
[相关TDR] TDR-003
[来源标注] [TD:ADR-006] [PRD:F-008.AC-1]
```

## TDR-008 LLM 主备模型：Deepseek-v4-flash + Qwen-turbo

```
[决策编号] TDR-008
[决策标题] LLM 主备模型：Deepseek-v4-flash + Qwen-turbo fallback
[决策状态] 已接受
[决策内容] M-006 主 LLM 使用 Deepseek-v4-flash（1M context），5xx 3 次后切 Qwen-turbo
[决策理由]
  1. Deepseek-v4-flash 实测 1M context，超过 20k token 需求 50x
  2. 中文场景 CER 优
  3. OpenAI 兼容 API
  4. Qwen-turbo 商业稳定作为 fallback
[拒绝的替代方案]
  - GPT-4o: 成本高
  - Claude: 不可用区域
  - 本地 LLM: 资源消耗大
[影响范围] M-006 / TS-007 / TS-008
[相关TDR] TDR-002
[来源标注] [调研:V1.0-src-tech-19/31] [TD:PC-004]

[决策编号] TDR-011

[决策状态] 已接受（V2.0 实施）
[决策内容] V2.0 阶段将 M-004 内部 sqlite 实现替换为 Redis + 云端，双写 14 天后切读

  - 直接切 Redis: 迁移期无 rollback 保障
  - 保留 sqlite 主存 + Redis 缓存: 复杂度高
[影响范围] M-004 实现（接口不变）
