## 方案 A：混合架构（管道-过滤器 + 分层 + 横切）★ 主方案

```
[方案编号] 方案 A
[方案名称] 混合架构（管道-过滤器核心 + 分层编排 + 横切错误/日志）
[架构模式] 混合（基于 4.8.1 决策树"混合特征"分支）
[核心思路]
  - 核心主链（URL → 下载 → 缓存 → 转写 → LLM → 笔记组装 → 落盘）采用管道-过滤器架构，数据单向流动
  - CLI 入口与并发调度采用分层架构，明确层级依赖
  - 错误处理与日志作为横切关注点，统一上报
  - LLM 与外部 API 通过 HTTP 适配层隔离（独立客户端模块）
[模块数] 12（M-001 ~ M-012）
[预估成本]
  - 开发人力: 5 人月（5 棒流水线 5 人 × 1 月）
  - 基础设施: 0（单机部署，用户自带硬件）
  - 运维成本: 0.2 人月/月（用户自助）
  - 学习成本: 2 人周（asyncio + yt-dlp + faster-whisper + 既有管道）
[优点]
  - 模块职责清晰（管道单向 + 分层 + 横切）
  - 易于扩展（管道节点可独立增加/替换）
  - 错误处理统一（横切不污染主链）
  - 与既有 5 阶段管道自然衔接
[缺点]
  - M-001 编排器需熟悉所有下游接口（学习成本集中）
  - 异步编程心智负担（asyncio + spawn 混合）
```

## 方案 B：纯分层架构（CLI → Service → Repository）

```
[方案编号] 方案 B
[方案名称] 纯分层架构（CLI → Service → Repository）
[架构模式] 分层（基于 4.8.1 决策树"功能主题数 ≤ 3 且主题间耦合度高"分支）
[核心思路]
  - 分 3 层: Presentation (CLI) / Service (业务逻辑) / Repository (数据访问)
  - Service 层 6-8 个服务（DownloadService / TranscribeService / LLMService / ...）
  - Repository 层 4-5 个仓储（FileRepository / CacheRepository / LogRepository / ...）
  - 各层间通过 DTO 传递数据
[模块数] 13（1 CLI + 7 Service + 5 Repository）
[预估成本]
  - 开发人力: 6 人月（分层 boilerplate + DTO 维护）
  - 基础设施: 0
  - 运维成本: 0.2 人月/月
  - 学习成本: 1 人周（标准分层）
[优点]
  - 模式标准，团队熟悉度高
  - 数据访问与业务逻辑分离
  - 单元测试简单（mock Repository）
[缺点]
  - DTO 维护成本高（14 个 DE × 多层 = 大量 boilerplate）
  - 管道语义丢失（DownloadService 内部需手动编排 download→cache→return）
  - 异步管道在分层中实现笨拙（async 跨层传播）
  - 错误处理散落各 Service，缺少横切
```


**[场景差异标注]**
- **方案 A 更适合**：需要管道语义清晰、未来可能扩展为多平台下载 / 分布式部署的场景
- **方案 B 更适合**：团队纯分层经验、且不预期 V2.0 演进的内部工具

**[TD 最终决策]**
虽方案差 < 5，但 V1.1 PRD 明确要求支持未来扩展（F-007 多平台、F-008 并发、F-016 知识树），且 SA 已定义预检/缓存/降级等横切关注点（BP-002/BP-007/BP-012），方案 A 与 SA 业务方案契合度显著高于 B。
- 选择方案 A
- 借鉴方案 B 的部分优点：M-008 PipelineNote 仓储层用 Repository 模式隔离文件系统（已体现为 M-008 独立模块）
- 借鉴方案 B 的部分优点：M-004 缓存内部用 Repository 模式（已体现为 M-004 独立模块）
