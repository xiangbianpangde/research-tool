## P1 - 代理 127.0.0.1:10809 未开，web 源（DDG）全挂

- **现象**：`research run` collect 阶段，web 源对所有子引擎（duckduckgo/google/brave/yahoo/wikipedia 等）报 `ConnectError: tunnel error: tcp connect error > Connection refused (os error 61)`，web 源零产出。
- **根因**：`config.yaml` 的 `collector.proxy: ${HTTPS_PROXY}`，`.env` 设 `HTTPS_PROXY=http://127.0.0.1:10809`，但该代理进程未运行。此代理是**国内环境**为翻墙访问 DDG/Wikipedia/GoogleNews/Tavily 配置的；本机位于日本，DDG/Wikipedia 直连可达，代理非必需。
- **处置**：运行时禁用代理（`HTTPS_PROXY=''` 或 unset），让 web 源走直连。后续若回国需重新开代理。
- **状态**：✅ 已绕过（直连可用）。建议 config 增加按地理环境切换代理的说明，或 `proxy` 留空时自动直连。

## P2 - 调研主题过长导致 slug 超 macOS 文件名限制

- **现象**：`research run "<超长中文主题...>"` 报 `OSError: [Errno 63] File name too long`，slugify 把整段中文转拼音生成 >255 字节的目录名。
- **根因**：`slug.py` 对超长主题未截断，macOS 文件名上限 255 字节。
- **处置**：用短主题（如"论文演讲视频关联匹配"），靠 `--llm-expand` + deepen 展开子查询。
- **状态**：⚠️ 已绕过（短主题）。**根因未修**--`slug.py` 应对 slug 做长度截断（如截到 80 字符 + hash 后缀）。登记为待修 bug。

## P3 - logs 目录路径假设错误

- **现象**：首次后台启动 `nohup research run ... > logs/talk-linker-research.log` 立即退出，因项目根无 `logs/` 目录。
- **根因**：日志目录实际在 `research-output/logs/`，非项目根 `logs/`。
- **处置**：改用 `research-output/logs/` 路径。
- **状态**：✅ 已绕过。属操作失误，非代码问题。

## P4 - 参考实现 cvf_backend.py 正则对真实 CVF 页面 0 命中

- **现象**：参考实现（Downloads/files.zip）的 `CVFBackend` 正则 `<dt\s+class="ptitle">\s*<a href=...>` 对 `openaccess.thecvf.com/CVPR2024?day=all`（2716 篇）命中 **0 篇**。

## P9 - SDK 默认 max_retries=2 让超时补丁失效

- **现象**：打上 P8 的 `httpx.Timeout(read=180)` 补丁后，organize 仍 0% CPU 挂 4+ 分钟。
- **根因**：anthropic SDK 0.116 默认 `max_retries=2`，单次 LLM 慢响应时 SDK 内部指数退避重试 2 次：read=180s × 3 ≈ 9 分钟才最终报错，与"立即失败"预期不符。
- **处置**：给 `AsyncAnthropic` 加 `max_retries=0`。
- **状态**：✅ 补丁完成。完整验证见 P10。

## P10 - dotenv 重新加载 .env 中的 HTTPS_PROXY（最隐蔽的根因）

- **现象**：打完 P8（超时）和 P9（max_retries=0）后，跑 organize 仍立即报 `Connection error`（进程 <1s 退出，日志 1 行）。
- **根因**：P1 仅在 shell 层 `unset HTTPS_PROXY`，但 Python 进程启动后 `load_dotenv('.env', override=False)` 会从 `.env` 文件**重新 setenv** `HTTPS_PROXY=http://127.0.0.1:10809`，导致 httpx 仍走不存在的 10809 代理，报 `ConnectError`。这是 P1 的真正根因——shell 层 unset 不够，必须在 LLM 客户端层显式禁用代理。
- **处置**：给 `anthropic_client.py` 加显式 `httpx.AsyncHTTPTransport(proxy=None)` + 自定义 `http_client` 传给 `AsyncAnthropic`，确保无论环境变量如何都直连。同步把 `read=180` 收紧到 `read=120`（与 max_retries=0 配合，最大失败时间 ~2 分钟）。
- **状态**：✅ 已修复并验证（独立 `chat()` 调用 3.3s 返回 OK）。这是 P6/P7/P8/P9 共同的真正上游根因。

## P11 - nohup + INFO→stdout 行缓冲导致"假挂起"误判

- **现象**：P10 修复后跑后台 organize+report，进程持续 0% CPU、日志文件 0 字节、看不到任何阶段推进，但实际进程在持续做事。
- **根因**：`logging_config.py` 把 INFO 路由到 `sys.stdout`，而 Python stdout 在 nohup+文件重定向下默认**全缓冲**（4KB 才 flush），外观察像挂起。stderr 是无缓冲（line-buffered）。
- **处置**：用 `research --verbose` 让 INFO/DEBUG 走 stderr（立即可见），或用 `stdbuf -oL -eL` 强制 stdout 行缓冲。两种都行，前者更简单。
- **状态**：✅ 已绕过。这是"假挂起"误判，organize 实际在 4-5 分钟内完成了 7 节点知识树。

## 经验沉淀（供后续会话）

- **判断"挂起"的两步法**：
  - 进程 CPU 0% 持续 3+ 分钟 + 状态 SN + 无子进程 + 无 socket → **真挂起**
  - CPU 0% + 状态 SN + 但日志 0 字节 + `lsof -p PID | grep sock` 偶尔有 socket → 大概率 stdout 行缓冲**假挂起**，用 `--verbose` 或 DEBUG 独立测试验证
- **nohup 后台跑 + 监控**：用 `research --verbose`（DEBUG→stderr，无缓冲）+ `tail -f log | grep -E "ERROR|完成|阶段|节点"` 实时追踪。
- **MiniMax 端点健康监测**：curl `https://api.minimaxi.com/anthropic/v1/messages` 平均 3.3-4.6s 响应；突发慢响应需配合超时机制（120s read）兜底。
- **管道自愈能力**：organizer 对 JSON 解析失败会自动重试（结构化输出失败 → 重发 → 大多成功），不要因部分 JSON escape 错误就 kill 整个管道。
- **三代理设计实践**：(a) P9+P10 的根因链揭示一个模式——"超时补丁"被 SDK 默认行为绕过，再被代理设置绕过，必须在"最底层"（客户端显式构造）做防御；(b) P11 揭示"假挂起"和"真挂起"在 CPU/状态字段上完全一样，必须看日志和 socket 区分。

## P12 - `_http.get_json` 被 dotenv HTTPS_PROXY 劫持，DBLP/直连源 ConnectError（2026-07-13）

- **现象**：`curl https://dblp.org/...` 正常返回 JSON；`CvprBackend` 经 `get_json` 报 `ConnectError: All connection attempts failed`。独立 `httpx.AsyncClient(trust_env=False)` 可通。
- **根因**：`_http._get` 在 `proxy=None` 时仍用 httpx 默认 `trust_env=True`，从环境 / dotenv 读到 `HTTPS_PROXY=http://127.0.0.1:10809`（代理未开）→ 全源连接失败。与 P1/P10 同族问题（代理隐式污染），但落在搜索 HTTP 层而非 LLM 客户端。
- **处置**：`_http._get` 在无显式代理时设 `trust_env=False`；需要代理只走 `config.proxy` → `set_default_proxy`。另：DBLP `venue:CVPR <q>` 组合偶发 Unknown Error/0 命中，`cvpr_backend` 改为关键词 + `CVPR` 文本锚，venue 严格过滤放客户端。
- **状态**：✅ 已修。live：`cvpr` 搜 "VGGT geometry" 命中 CVPR 2025 *VGGT: Visual Geometry Grounded Transformer*（openaccess.thecvf.com）。
